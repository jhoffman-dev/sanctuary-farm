# Sign-in without personal data

How a child gets back to their farm from another device, with nothing about
them ever collected. Implements ADR-0002 (SF-113, issue #161); the save schema
and rules it feeds are SF-114 (`docs/cloud-save.md`, `firestore.rules`).
Code: `functions/src/auth/`.

**Nothing personal is ever asked for or stored:** no name, age, email, phone,
location or photo. Every credential is generated by the server. The Firebase
Auth user created for a farm has an opaque uid and no profile fields at all.

## 1. The flows

Three callable Cloud Functions in the `sanctuary-farm` codebase (region
`us-central1`), reachable only from the game's Hosting origins
(`https://sanctuary-farm.web.app`, `https://sanctuary-farm.firebaseapp.com`;
the emulator adds `localhost:5000`).

| Function | Takes | Returns |
| --- | --- | --- |
| `createAccount` | `{ withUsername?: boolean }` | `{ token, saveCode }`, plus `{ username, pin }` when asked — **shown once**, never retrievable again |
| `signInWithCode` | `{ code }` | `{ token }` |
| `signInWithUsernamePin` | `{ username, pin }` | `{ token }` |

`token` is a Firebase **custom token** for the farm's uid; the client passes
it to `signInWithCustomToken`. Its only custom claim is
`{ game: 'sanctuary-farm' }` — required by the rules, because Auth is shared
with the other games in `student-games-be188` (SF-114).

Every farm gets a save code; the username + PIN is an optional convenience on
top. The save code is the root credential (threat model row 4): a PIN lockout
never locks a child out of their farm, and "Delete my farm" will need the code.

Refusals are deliberately few and kind, and never say whether a farm exists:

| Status | Message the child sees | When |
| --- | --- | --- |
| `invalid-argument` | Check what you typed and try again. | The input cannot be a code / username / PIN at all |
| `unauthenticated` | That didn't match. Check it and try again, or use your farm code. | Unknown code, unknown username **and** wrong PIN — identical answers, and the same scrypt work on each path |
| `resource-exhausted` | Let's take a little break. Try again soon. (`details.retryAfterSeconds`) | Rate limit or PIN lockout |

## 2. Save codes

`FARM-7K4QX-MN3TD-9HWAC`: a fixed `FARM` prefix and **15 symbols** in three
groups of five, from a **27-symbol alphabet** `23456789ACDEFGHJKMNPQRTVWXY` —
no 0/O, 1/I/L, 2/Z, 5/S, 8/B or U/V for a child to confuse. Drawn from the
platform CSPRNG with rejection sampling (no modulo bias).

**Entropy: 15 × log2(27) ≈ 71.3 bits** (2.95 × 10²¹ codes). The threat model
asks for ≥ 60. Input is forgiving: case, spaces, dashes and the prefix are
optional.

**Why enumeration is infeasible.** Each address gets 100 sign-in attempts per
10 minutes (§5) = 14,400 a day. Suppose a million farms exist (2²⁰) and an
attacker runs **10,000 addresses for a year**: 5.3 × 10¹⁰ guesses (2³⁵·⁶),
each hitting some farm with probability 2²⁰ / 2⁷¹·³. The chance of finding
*any* farm in that year is about **1 in 50,000**. At a realistic scale (one
attacker, three addresses, a year) it is about 1 in 100 million.

Codes are reusable bearer credentials: signing in twice with one code works
(a child plays on two devices). "Get a new code" (revoke + reissue) is a later
ticket alongside the parent gate.

## 3. Usernames and PINs

**Username:** adjective + animal + two digits, e.g. `BraveOtter42`, from
hand-curated lists in `functions/src/auth/domain/kidSafeWords.ts` — 64
adjectives × 64 animals × 86 numbers = **352,256** names. Never typed or
chosen by a child, so it carries no identity and no free text. Numbers 14, 18,
69 and 88 are excluded. Sign-in folds case and spaces.

**Blocklist:** `username.test.ts` builds **every one of the 352,256 names** and
checks each, whole (so words formed across a join are caught), against a broad
blocklist of profanity, slurs, body/drug/violence words and coded numbers. It
earned its place on day one: `GoldenIguana` contains a slur fragment and the
animal was swapped for `Impala`. Any list change re-runs it.

**PIN:** **4 digits, generated by the server**, not chosen. A child-chosen PIN
is very often a birthday or birth year — personal data — or `1234`. Sign-in
accepts 4–6 digits so the length can grow without breaking existing farms.

## 4. Hashing

| What | How | Why |
| --- | --- | --- |
| Save code | HMAC-SHA256 under the pepper → document id | A high-entropy code needs a fast, deterministic lookup, not a slow hash. Without the pepper a leaked database is useless; with it, 71 bits still cannot be searched |
| PIN | scrypt (N = 2¹⁵, r = 8, p = 1, 16-byte salt, 32-byte key) over HMAC(pepper, PIN) | A 4-digit PIN has 10,000 values: scrypt alone would fall in seconds offline. The pepper is what protects it; scrypt is the second layer |
| Throttle keys (address, typed username) | HMAC under the pepper → document id | Neither an IP address nor whatever was typed into the username box is stored |

Hashes are purpose-separated (`saveCode` / `pinAttempts` / `clientAddress`).
scrypt is Node's built-in `crypto.scrypt` — no new dependency (threat model
row 10), identical on the `nodejs22` runtime and the emulator's host Node. The
stored form `scrypt$15$8$1$<salt>$<hash>` carries its own cost so it can be
raised later. A missing or short (< 32 chars) pepper makes the function refuse
to start rather than hash weakly.

## 5. Rate limits and lockout

**Per address** (fixed window, Firestore transaction on a counter document;
the address is the right-most `X-Forwarded-For` entry, the one Google's front
end appends):

| Policy | Limit | Why that number |
| --- | --- | --- |
| Sign-in (code and username + PIN share it) | **100 per 10 minutes** | A class of 30 behind one school address, each mistyping a couple of times |
| Create account | **60 per hour** | A whole class setting up at once, twice over |

**Per username** (`PIN_LOCKOUT_POLICY`): **5 free wrong PINs**, then a wait of
**1, 2, 4, 8 … minutes**, doubling per further failure, **capped at 24 hours**;
a correct PIN clears it; 30 quiet days forget it. Every attempt is counted
*before* the PIN is checked (cleared on success), so parallel guesses cannot
race past the count.

The lockout is keyed by the HMAC of the *typed* username, whether or not that
account exists — so an unknown name locks out exactly like a real one and the
lockout itself is no "does this user exist" oracle. That is why lockout state
lives in `authPinAttempts`, not inside `usernames/{username}`.

**What it buys.** A kind path for a seven-year-old: five tries, then a
one-minute break. Against a determined guesser of one account: about 15
guesses on day one (5 free, then waits summing to ~17 hours), then about one a
day — roughly **380 guesses a year, under 4 % of the 10,000-PIN space**. Going
quiet for 30 days to reset buys only 15 more per month, which is slower. A
classmate who learns a username can make it wait, but cannot lock the child
out: the save code still works. That residual risk is accepted because the PIN
is a convenience, not the root credential (threat model row 4).

## 6. What is stored

All in the named database **`sanctuary-farm`**, all server-only — the SF-114
rules deny every client access to these collections (and to any path they do
not name). Field lists are asserted exactly by the emulator tests.

| Document | Fields | Lifetime |
| --- | --- | --- |
| `saveCodes/{HMAC(code)}` | `uid` | With the farm |
| `usernames/{username, lower case}` | `uid`, `pinHash` | With the farm |
| `authRateLimits/{HMAC(window, address)}` | `windowStartedAt`, `count`, `expiresAt` | Until its window ends (TTL) |
| `authPinAttempts/{HMAC(typed username)}` | `failures`, `lastFailureAt`, `expiresAt` | 30 days after the last failure (TTL) |

No timestamps of sign-ins, no device, no address, no plaintext code or PIN.
Firebase Auth holds one user per farm: the uid (`sf-` + 128 random bits), no
email, name, phone or photo. Our code logs nothing about a caller; the
platform's request logs (which include addresses) are internal-operations only
with short retention (ADR-0002).

## 7. What James must configure before the first deploy

Nothing below is in git; agents do not run it (`docs/secrets.md` rule 3).

```bash
# 1. The pepper — generate locally, paste when prompted. Never commit, never share.
openssl rand -base64 48
firebase functions:secrets:set SANCTUARY_FARM_AUTH_PEPPER --project student-games-be188

# 2. Custom tokens are signed by the functions' runtime service account via IAM:
#    let it sign as itself, and make sure the IAM Credentials API is on.
gcloud services enable iamcredentials.googleapis.com --project student-games-be188
gcloud iam service-accounts add-iam-policy-binding \
  <PROJECT_NUMBER>-compute@developer.gserviceaccount.com \
  --member="serviceAccount:<PROJECT_NUMBER>-compute@developer.gserviceaccount.com" \
  --role=roles/iam.serviceAccountTokenCreator --project student-games-be188

# 3. TTL so stale throttle documents delete themselves (named database!).
gcloud firestore fields ttls update expiresAt --collection-group=authRateLimits \
  --enable-ttl --database=sanctuary-farm --project student-games-be188
gcloud firestore fields ttls update expiresAt --collection-group=authPinAttempts \
  --enable-ttl --database=sanctuary-farm --project student-games-be188

# 4. Deploy rules (SF-114) before functions, then the functions codebase only.
pnpm deploy:rules
pnpm deploy:functions
```

The pepper is **permanent in practice**: changing it orphans every save code
and PIN (their hashes no longer match). Rotate only after a leak, and expect
every child to need a new code. Keep a copy in James's password manager.

### After deploying

- Call `createAccount` from the game origin and sign in with the code.
- **Check the address the rate limiter sees:** from one network, 101 quick
  `signInWithCode` calls with a junk code should get `resource-exhausted` on the
  101st, and a phone on mobile data should still get through. If *everyone*
  shares one bucket, `X-Forwarded-For` has an extra Google hop on this runtime
  and `clientIpOf` must take the entry before it.

## 8. Tests

- **Unit** (`pnpm test:functions`, in `pnpm gate`): codes (shape, alphabet,
  entropy, bias, normalisation), word lists and the full blocklist sweep, PIN
  generation, lockout schedule and forgetting, rate windows, hashing
  round-trip / salt / pepper / malformed hash, and every use-case with fakes:
  happy paths, collisions, wrong PIN ≡ unknown user, lockout, rate limits,
  malformed input. Coverage floor: domain 95 %, application 90 %.
- **Integration** (`pnpm test:auth`, CI `rules` job): Functions + Firestore +
  Auth emulators on `demo-sanctuary-farm`. Adapters round-trip and fail loudly
  on malformed records; concurrent counter updates are exact; the minted token
  carries exactly `{ game: 'sanctuary-farm' }` and signs in at the Auth
  emulator; end to end over HTTP: create, sign in both ways, unknown/replayed
  code, wrong PIN, lockout (and the save code still works), per-address rate
  limit, malformed bodies, and an exact field-list and no-plaintext check on
  every stored document.
