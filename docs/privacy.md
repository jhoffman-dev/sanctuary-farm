# Privacy notice (draft)

> **Draft — pending legal review (SF-35).** This notice is written to be true of
> the current alpha (local save only) and of the Phase 4 cloud-save design in
> ADR-0002. It has not yet been checked by a lawyer. Any feature that changes
> what the game stores, where, or for how long must update this document in the
> same PR — the notice is only worth having if it stays true.

## For kids

Sanctuary Farm remembers your farm so it is there when you come back.

It remembers your animals, your coins, your feed, and which sums you are quick
at and which ones still need practice. That is all.

The game never asks for your name, your age, your school, your email, a photo,
or where you live. It does not need to know who you are.

If you save your farm to the cloud, the game gives you a **save code**. A save
code is like a key to your farm. Keep it somewhere safe. Do not give it to
anyone except a grown-up you trust.

The game can also give you a **farm name**, like *BraveOtter42*. The game makes
it up — you do not type it, so it is never your real name.

There are no ads in Sanctuary Farm and there is nothing to buy. Ever.

If you want the game to forget your farm, ask a grown-up to help you press
**Delete my farm**. Once it is gone, it is gone.

## For parents and teachers

**What exists and where.** In the current alpha, the game stores a single save
in the browser's `localStorage` on the device it is played on. Nothing leaves
the device. In Phase 4, an optional "Save to the cloud" action will copy that
save to a Firestore document (Google Firebase) keyed by an anonymous, random
save id. Cloud saving is opt-in per farm; local play keeps working without it.

**Exactly what a save contains.** A save is a small structured record made of:

- Per multiplication fact (e.g. 7×8): which Leitner box it is in, when it is
  next due (counted in questions asked, not clock time), the last few answer
  times in milliseconds, correct streak, total attempts, total correct.
- Which tiers of facts are unlocked and the highest table in play.
- Coins and feed counts.
- Session logs: a start and end time (clock timestamp), where on the farm the
  round happened, which fact family was practised, and for each question the
  fact asked, the number typed, whether it was right, and the answer time.
- Settings: sound muted or not, highest table.
- A schema version number.

There is no name, no free-text field, no photo, no avatar description, and no
device identifier anywhere in the save. A save cannot identify a child.

**What is not collected.** No name, age, date of birth, email, phone number,
postal address, school, class, photo, voice, or location. No geolocation from
IP address. No advertising identifiers. **No third-party analytics or tracking
SDKs** of any kind are loaded — no Google Analytics, no session replay, no
pixels. *Note:* the project still has to decide its analytics stance (SF-31).
The current recommendation is none for the alpha; if any aggregate,
identifier-free counting is ever added, this notice must be updated first.

**Cookies.** The game sets no cookies of its own and stores nothing in the
browser beyond the save described above. Firebase Hosting, which serves the
files, may set the minimal cookies it needs to deliver the site; we do not read
them or use them for anything.

**Identity model.** There are no accounts in the usual sense.

- A **save code** (e.g. `farm-7K2P-9QXM`) is a random secret minted by the
  server when a farm is first saved to the cloud. It is the only credential.
  We store a hash of it, not the code itself, so it cannot be recovered if lost.
- A **username + PIN** is an optional convenience for kids who find codes hard
  to keep. The username is generated by the game (e.g. `BraveOtter42`) and is
  never typed by the child; the PIN is four digits chosen by the child. We
  store the username and a hash of the PIN. Sign-in goes through a Firebase
  Cloud Function using Firebase custom auth. No email or password is involved.

We believe this satisfies COPPA's "support for internal operations" exception:
the only persistent identifier is used to give a child back their own farm, and
it is never used for advertising, cross-site tracking, or building a profile.
This reasoning is pending legal review and should not be relied on until then.

**Sharing.** Visiting a friend's farm by code (a planned feature) is read-only
and shows only the farm itself — animals, layout, and pre-set sign phrases. No
free text written by one child is ever shown to another. Nothing in a farm view
identifies the child who owns it.

**Retention and deletion.** *Proposed:* cloud saves not loaded or saved for
**12 months** are deleted automatically. A **Delete my farm** action removes the
cloud save, the save-code hash, and any username and PIN hash; it requires the
save code so that nobody else can delete a child's farm. Deletion is immediate
and permanent — we keep no backups of deleted saves beyond Firebase's own
short-lived operational backups (period to be confirmed). A local save is
deleted by clearing the site's data in the browser, or via the same in-game
action.

**Children under 13.** Most players are under 13. Because there are no
accounts, no PII, and no persistent identifier used for anything other than
restoring a farm, we do not currently run a verifiable-parental-consent flow.
This is the central point for legal review.

## Data inventory

| Data | Where | Why | How long | Deleted how |
| --- | --- | --- | --- | --- |
| Farm save (scheduler state, coins, feed, settings) | Browser `localStorage`; Phase 4: Firestore document keyed by anonymous save id | Restore the farm between visits | Local: until cleared. Cloud (proposed): until 12 months inactive | Clear site data; "Delete my farm" (needs save code) |
| Session logs (timestamps, fact ids, answers, latencies — no content) | Inside the farm save | Scheduling and mastery; kids' own "best" comparisons | Same as the save | Same as the save |
| Settings (muted, max table) | Inside the farm save | Remember preferences | Same as the save | Same as the save |
| Save code hash | Firestore (Phase 4) | Verify the code on load / delete | Same as the cloud save | Deleted with the farm |
| Username (generated) | Firestore (Phase 4) | Optional sign-in without a code | Same as the cloud save | Deleted with the farm |
| PIN hash | Firestore (Phase 4) | Verify the child's 4-digit PIN | Same as the cloud save | Deleted with the farm |
| Hosting logs (Firebase's own; include IP address, user agent, URL) | Google Firebase Hosting | Serve the site; abuse and outage diagnosis | Firebase's default retention — *to confirm; we believe ~30 days* | Not deletable by us per-user; never joined to saves or analysed |
| Teacher feedback form entries (Phase 5) | Firestore | Improve the game | *Proposed:* 24 months | Manually on request; no PII by design (pick-from-options plus a short text field that asks for none) |

## Open questions for legal review

- Does the save-code / generated-username model fit COPPA's internal-operations
  exception well enough that no verifiable parental consent is needed? Does a
  child-chosen 4-digit PIN change that analysis?
- Do session timestamps plus answer latencies count as "persistent identifier"
  or behavioural data in any jurisdiction we care about (US states, UK, EU)?
- Firebase Hosting IP logs: exact retention, whether Google is a processor or
  service provider under COPPA / state law, and whether a data-processing
  addendum is needed.
- Is 12 months the right inactivity period for cloud saves? Is a "kept until
  deleted" option acceptable for classroom use?
- FERPA / state student-privacy laws (e.g. SOPIPA, NY Ed Law 2-d): is "no PII,
  no education records" sufficient if a school or district adopts the game, or
  do we need a template agreement?
- Should the notice be shown before a child's first cloud save, on the landing
  page only, or both? Does the kid-readable version need to appear in-game?
- The teacher feedback form (Phase 5) will accept a short free-text field from
  adults. Confirm that is acceptable given it is not child-facing.
- The contact method: is an email address sufficient, and must it be monitored
  within a set time for deletion requests?
